**`/sync-work`** brings the [Economics](/things/economics) mirror up to date —
from the last synced date to now — and tells you what changed: new sessions,
tokens, API cost, and active time, per client.

It wraps `npm run econ:sync` in the `things` repo, which is a **full, idempotent
rescan** of `~/.claude/projects` — so there is no cursor to manage and running
it twice is harmless.

## Using it

```
/sync-work
```

That's the whole interface. No arguments.

## What it does

<Steps>
  <Step title="Read the last sync">
    Queries `econ_sync_runs` through the **Supabase MCP** (`execute_sql`) for
    the latest `run_at` and its totals — this is the "since" date the report is
    anchored on.
  </Step>
  <Step title="Run the sync">
    `npm run econ:sync` from the `things` repo. Pushes through the Supabase
    Management API (`SUPABASE_ACCESS_TOKEN`) — the same channel the MCP uses —
    falling back to the service-role client (`SUPABASE_SECRET_KEY`); with
    neither, it emits `--sql` and applies the script through the Supabase MCP.
  </Step>
  <Step title="Report the delta">
    Diffs the new `econ_sync_runs` row against the previous one (sessions,
    tokens, cost) via the MCP and lists the clients whose sessions advanced
    past the old `run_at` — so the summary reads "since July 4: 12 sessions
    across TFLC, Picotin, Things — 89M tokens, est. $41.20".
  </Step>
</Steps>

<Warning>
  Only run it on the machine that holds the session logs. An empty scan followed
  by the prune step would wipe the mirror — see the
  [Economics runbook](/things/economics) for why.
</Warning>

<Note>
  Pricing, the active-time heuristic, and the exact table shapes are documented
  in [Economics](/things/economics). If a model shows up costing $0, add it to
  the `PRICE` table in `scripts/econ-sync.ts` and run `/sync-work` again.
</Note>
