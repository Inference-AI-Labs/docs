## One Azure app, many tenants

Every Flow app signs in through a **single multi-tenant Azure app registration**
called `flow`. We do **not** register an app per client. Each tenant is kept
apart by two things: its own Supabase project and an email-domain check in its
own code.

| Setting | Value |
| --- | --- |
| App name | `flow` |
| Client ID | `15161a71-35f9-4dc9-8d95-0c3ab8350272` |
| Home directory | `kinference.onmicrosoft.com` (tenant `1ad867c7-…`) |
| Sign-in audience | `AzureADMultipleOrgs`, so any organisation's work accounts |
| Secret | one secret, hint `Hl0…`, expires **2028-05-21** |

Microsoft is used in two places, and each reads the keys from somewhere different:

| Path | What it does | Reads keys from | Callback |
| --- | --- | --- | --- |
| **Sign-in** | Staff sign in to the app | The Supabase project's **Azure provider** (dashboard → Authentication → Providers → Azure) | `https://<ref>.supabase.co/auth/v1/callback` |
| **Mailbox (Graph)** | Refreshes the Graph tokens saved at sign-in, and runs the Talents connector | The app's **env vars**: `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET` and `MICROSOFT_TENANT_ID` | `https://<app>.takeflow.io/api/talents/microsoft/callback` |

Both paths use the same client ID and secret. If either side is missing,
that path breaks and the other one keeps working, so a half-configured
tenant can look fine at first.

## The tenant setting

The tenant only decides **which organisations Microsoft will offer a login
for**. It does not decide who gets into the app.

- **`common`**: any organisation. This is the default for client apps.
- **A tenant ID**: that one organisation only. Use it only when the client explicitly wants it.

Who actually gets in is decided by `ALLOWED_DOMAINS` in
`app/auth/callback/route.ts`. With `common`, **that check is the only gate**.
A disallowed account can finish the Microsoft login, so the callback signs it
out and deletes the Supabase user it just created.

## Setting up a new tenant

<Steps>
  <Step title="Find the client's real Microsoft domain">
    Check that the domain the client's staff sign in with is on Microsoft 365:

    ```bash
    curl -s "https://login.microsoftonline.com/getuserrealm.srf?login=x@<domain>&json=1"
    ```

    You want `"NameSpaceType":"Managed"` (or `"Federated"`). `"Unknown"` means
    that domain is not on Microsoft, so staff can't sign in with it. Ask the
    client which domain they actually use.
  </Step>

  <Step title="Register the Supabase callback on the flow app">
    Add `https://<ref>.supabase.co/auth/v1/callback` to the app's web redirect
    URIs. `az ad app update --web-redirect-uris` **replaces** the whole list
    (and it rejects some lists outright), so patch it through Graph with the
    existing list plus the new entry:

    ```bash
    APP=15161a71-35f9-4dc9-8d95-0c3ab8350272
    OID=$(az ad app show --id $APP --query id -o tsv)
    az ad app show --id $APP --query "web.redirectUris" -o json \
      | python3 -c "import json,sys;u=json.load(sys.stdin);u.append('https://<ref>.supabase.co/auth/v1/callback');print(json.dumps({'web':{'redirectUris':u}}))" \
      > patch.json
    az rest --method PATCH --url "https://graph.microsoft.com/v1.0/applications/$OID" \
      --headers Content-Type=application/json --body @patch.json
    ```

    Add `https://<app>.takeflow.io/api/talents/microsoft/callback` the same way
    if the app uses the Talents mailbox connector.
  </Step>

  <Step title="Configure the Supabase Azure provider">
    On the tenant's Supabase project (**Authentication → Providers → Azure**):

    | Field | Value |
    | --- | --- |
    | Enabled | on |
    | Client ID | `15161a71-35f9-4dc9-8d95-0c3ab8350272` |
    | Secret | the `flow` app's secret, the same value as `MICROSOFT_CLIENT_SECRET` |
    | Azure Tenant URL | `https://login.microsoftonline.com/common` |

    Then under **Authentication → URL Configuration**, set **Site URL** to
    `https://<app>.takeflow.io` and add these to **Redirect URLs**:
    `https://<app>.takeflow.io/**` and `http://localhost:3000/**`.

    <Warning>
      With an empty Redirect URLs list, Supabase can ignore the app's
      `redirectTo` (`/auth/callback?next=…`) and fall back to the Site URL. The
      code never reaches `/auth/callback`, so the domain check never runs and
      the Graph tokens are never saved.
    </Warning>
  </Step>

  <Step title="Set the app's env vars">
    Add the three vars to `.env.local` and to Vercel production:

    ```bash
    printf '15161a71-35f9-4dc9-8d95-0c3ab8350272' | vercel env add MICROSOFT_CLIENT_ID production
    printf '<secret>' | vercel env add MICROSOFT_CLIENT_SECRET production --sensitive
    printf 'common' | vercel env add MICROSOFT_TENANT_ID production
    ```

    `MICROSOFT_REDIRECT_URI` is optional. Without it, the app uses
    `<origin>/api/talents/microsoft/callback`. Env var changes only take effect
    on the next deploy.
  </Step>

  <Step title="Set the domain check">
    In `app/auth/callback/route.ts`:

    ```ts app/auth/callback/route.ts
    const ALLOWED_DOMAINS = ["<client-domain>"];
    ```

    Also update any other place that decides who counts as staff, such as the
    task roster's `INTERNAL_DOMAIN` in `components/tasks/tasks-view.tsx`.
  </Step>

  <Step title="Deploy and test one real login">
    Push to `main`, then sign in once with a real client account. The first
    user may see a Microsoft consent screen for `flow`. If the client's IT
    doesn't let users approve apps themselves, one of their admins has to
    approve it once for the whole organisation.
  </Step>
</Steps>

<Warning>
  When you fork a Flow app from another client, **re-check every step above**.
  Forks carry over the other client's tenant URL on the Supabase provider, its
  `ALLOWED_DOMAINS`, and staff addresses rewritten with a find-and-replace on
  the domain. Fluitron shipped locked to TFLC's tenant and allowing
  `fluitron.ae`, a domain with no Microsoft account behind it. The real
  domain was `fluitron.com`.
</Warning>

## Verifying a tenant's config

Supabase never returns the Azure secret in plain text. `GET /v1/projects/<ref>/config/auth`
returns `external_azure_secret` as **HMAC-SHA256(key = project ref, message = secret)**.
To check it against the known secret without exposing it:

```python verify_secret.py
import hmac, hashlib
ok = hmac.new(ref.encode(), secret.encode(), hashlib.sha256).hexdigest() == stored
```

<Note>
  Compare that hex value directly. Hashing it again gives a false "mismatch",
  and that exact mistake has happened before.
</Note>

Other checks:

- **Is the secret still valid?** Request a `client_credentials` token from the
  `kinference` tenant with it. A token back means yes.
- **Which tenant is a URL pointing at?** Look it up with
  `az rest --url "https://graph.microsoft.com/v1.0/tenantRelationships/findTenantInformationByTenantId(tenantId='<id>')"`.
- **Does the login start correctly?** Opening
  `https://<ref>.supabase.co/auth/v1/authorize?provider=azure` should redirect
  to `login.microsoftonline.com/common/…` with `client_id=15161a71…`.

## When a login fails

Work backwards along the path: Microsoft → Supabase → the app's callback. The
error text says which leg broke.

| What the person sees | Where it broke | Cause |
| --- | --- | --- |
| The address bar shows the Supabase host twice, e.g. `…supabase.cohttps//…supabase.co` | Before Microsoft | `NEXT_PUBLIC_SUPABASE_URL` holds its value twice. See below. |
| `AADSTS50020: User account … does not exist in tenant '<other client>'` | Microsoft | The Supabase provider's **Azure Tenant URL** points at another client's tenant. Set it to `common`. |
| `AADSTS650051: … service principal name is already present` | Microsoft | Transient, on the first-ever login from that organisation. Microsoft sets the app up mid-request and reports an error doing it. **Retry once**; the second attempt goes through. |
| `AADSTS50011: redirect URI mismatch` | Microsoft | `https://<ref>.supabase.co/auth/v1/callback` is missing from the `flow` app's redirect URIs. |
| `Invalid API key` | The app's callback | The app's Supabase publishable key is wrong, so `exchangeCodeForSession` is rejected before it reaches the auth server. |
| `This account isn't allowed to sign in.` | The app's callback | The account's domain is not in `ALLOWED_DOMAINS`. On a forked app this is usually still the previous client's domain. |

<Note>
  The last two happen **after** Microsoft and Supabase have both succeeded, so
  the Microsoft side can look perfect while every login still fails.
</Note>

### Read the logs

Supabase's auth logs show how far each attempt got. `/authorize` without a
matching `/callback` means Microsoft rejected it; the `/callback` line carries
the `AADSTS…` text.

```bash
curl -s -G -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
  "https://api.supabase.com/v1/projects/<ref>/analytics/endpoints/logs.all" \
  --data-urlencode "sql=select timestamp, event_message from auth_logs order by timestamp desc limit 40" \
  --data-urlencode "iso_timestamp_start=2026-09-22T15:40:00Z" \
  --data-urlencode "iso_timestamp_end=2026-09-22T16:00:00Z"
```

Then `vercel logs <deployment>` for the app's own leg. A `307` on
`/auth/callback` back to `/` is the callback bouncing the login.

The user table tells you the same story:

```sql
select email, created_at, last_sign_in_at from auth.users order by created_at desc;
```

- **A row with `last_sign_in_at` null** — Microsoft and Supabase finished, the app's callback then failed. Look at the app, not Microsoft.
- **No row at all, after a real attempt** — the domain check rejected it and deleted the user, exactly as `app/auth/callback/route.ts` intends.

### Env values pasted twice

Setting many Vercel vars in one go can store each value **doubled** — the URL,
the keys, everything. A doubled key gives `Invalid API key`; a doubled URL
gives the malformed address above.

Sensitive vars can't be read back (`vercel env pull` returns them empty), so
check the ones the browser receives by pulling them out of the live bundle and
comparing **lengths** against `.env.local`:

```bash
for js in $(curl -s "https://<app>.takeflow.io/" | grep -o '/_next/static/[^"]*\.js' | sort -u); do
  curl -s "https://<app>.takeflow.io$js" | grep -oE 'sb_publishable_[A-Za-z0-9_-]+|phc_[A-Za-z0-9]+'
done | sort -u | while read k; do echo "${k:0:20}… len ${#k}"; done
```

A publishable key is 46 characters; 92 means it was stored twice. Confirm a key
is live and valid with `curl -o /dev/null -w '%{http_code}' https://<ref>.supabase.co/auth/v1/settings -H "apikey: <key>"` — 200 good, 401 bad.

<Warning>
  Server-only values can't be checked this way at all. Verify
  `MICROSOFT_CLIENT_SECRET` by asking Microsoft for a `client_credentials`
  token with it before you trust it, and re-set anything you can't verify.
  Vercel only picks up new values on the **next deploy**, so redeploy before
  re-testing — otherwise you'll debug the old value.
</Warning>

## Localhost fallback

Production is Microsoft-only. For local development, `/login/fall` offers
email + password sign-in that **refuses any non-localhost host**. It exists so
that an admin outside the client's domain can still get in.
